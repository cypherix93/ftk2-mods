## 3. Patch targets for `rng.gameplayDraws` / `rng.visualDraws` counters

**Visual counter (`rng.visualDraws`) — straightforward, patch all four:**
- `GameRandom.NextChanceVisual`
- `GameRandom.NextFloatVisual` (both overloads)
- `GameRandom.NextNormalizedFloatVisual`

These are leaf-shaped (bare `Next*Visual` primitives with no other `GameRandom` method calling
them, going by name), so a Harmony prefix on each is a 1:1 draw count with no double-counting risk.

**Gameplay counter (`rng.gameplayDraws`) — two tiers, pick one deliberately:**

*Tier A — true primitives* (safe to patch without double-counting):
- `NextBool`
- `NextChance` (both overloads)
- `NextDecimal` (both overloads)
- `NextInt` (both overloads)
- `NextIntAscendingWeight`
- `NextIntDescendingWeight`
- `NextNormalizedDecimal`
- `NextNormalizedFloatDistributed`
- `NextOffset3`
- `NextPointInSphere`
- `NextPointInUnitSphere` (both overloads)
- `NextVector3`

*Tier B — composite selection helpers* (likely implemented on top of Tier A, most plausibly `NextInt`
for index selection):
- `GetRandomElementFromArray`
- `GetRandomElementFromList`
- `GetRandomElementFromWeightedList`
- `GetRandomKeyFromDictionary`
- `GetRandomValueFromDictionary`
- `ShuffleList`

**Recommendation:** patch Tier A only. If Tier B methods internally call a Tier A method (the
common pattern for "pick a random element" = "draw an index via `NextInt`, then index the
collection"), patching both tiers would double-count every table/loot/shuffle roll. This could not
be confirmed from signatures alone (no IL available via TypeProbe) — before wiring the S5 lint,
verify with a quick call-count sanity check (call `GetRandomElementFromList` once with counting
patches on both `NextInt` and the helper itself; if the gameplay counter increments by 2 instead of
1, Tier B is confirmed composite and must stay unpatched).
